# Фото лотов с Яндекс.Диска — задача для реализации

## Статус: реализовано (ветка `feat/yandex-disk-lot-photos`, 2026-08-21/22)

Ниже — исходный план **до** реализации; часть решений по ходу дела уточнили.
Актуальный порядок и код:

- Код: `apps/api/src/catalog/catalog.service.ts` (сбор `feedImageUrls` +
  `layoutUrl`) и `apps/api/src/catalog/yandex-disk-photos.service.ts`
  (`computePhotoOrder`, обход Я.Диска, кэш).
- **Итоговый порядок `Lot.photos`:** план → поэтажный план → персональные фото
  с Я.Диска → остальные фото фида — **всегда в этом порядке**, включая случай,
  когда персональных фото с Я.Диска не нашлось (план ниже предполагал в этом
  случае брать «все фото фида» вместо «план + остальные», но в итоге решили не
  усложнять: план фиксированно первый, а «остальные» — это просто весь фид
  минус то, что уже показано выше).
- **Источник 3 (общие фото проекта) сознательно не реализован** в этой
  итерации — только Источник 1 (по `externalId`) и Источник 2 (Soho, по
  номеру квартиры, фолбэк).
- **Обнаружилось в реальном фиде:** у оффера бывает 2-3 картинки с
  `type="plan"` (не одна, как предполагалось ниже). В `Lot.photos` попадает
  только первая — вторая и последующие **не идут даже в «остальные фото
  фида»**: это дублирующие рендеры планировки, которые и так по смыслу
  дублируют то, что несут персональные фото с Я.Диска, поэтому исключены
  из фида целиком (`catalog.service.ts` фильтрует все `type="plan"` кроме
  первого при сборе `feedImageUrls`).
- Отдельно есть `type="plan floor"` — поэтажный план (один на этаж, общий для
  всех юнитов на нём), которого исходный план вообще не учитывал. Он идёт в
  `Lot.photos` вторым, сразу после плана квартиры. Хранится в уже
  существовавшем, но раньше не заполнявшемся при синке фида поле
  `Lot.layoutUrl` (оно уже было в схеме — его заполнял только вебхук
  ProfitBase, из XML-фида не бралось).

## Зачем

На проекте старого сайта Зорге 9 (old.zorge9.com, отдельный PHP/Wolf CMS
проект, не этот репозиторий) сделали то же самое: к фото из фида ProfitBase
(там обычно 1-3 картинки, преимущественно просто планировка) для части лотов
добавили дополнительные фото с Яндекс.Диска — общий фотобанк, которым уже
пользуется проект `feed_enricher` (github.com/sereganikitin/feed_stm,
production https://feeds.infoseledka.ru) для фидов ЦИАН/Авито.

Нужно сделать то же самое здесь — в каталоге на stmichael.ru (корпоративный
сайт, этот репозиторий, apps/api + apps/web).

## Итоговый порядок фото по лоту

Для каждого лота фото должны идти в таком порядке:

1. **Первая (и только первая!) картинка из фида ProfitBase** — это планировка
   (`<image type="plan">`, всегда первая по порядку в XML).
2. **Персональные фото лота с Я.Диска**, если для этого лота они нашлись (см.
   ниже два источника — по id и по номеру квартиры).
3. **Общие фото проекта с Я.Диска** — одинаковые для АБСОЛЮТНО ВСЕХ лотов всех
   корпусов, в самом конце.

**Важно:** если для лота НЕ нашлось персональных фото с Я.Диска (шаг 2), то из
фида берутся **ВСЕ** его картинки, а не только первая — обрезаем до одной
картинки только тогда, когда реально есть, чем её дополнить. Общие фото проекта
(шаг 3) добавляются в любом случае, независимо от того, нашлись персональные
или нет.

## Откуда данные (ProfitBase)

Ничего менять не нужно — фид `apps/api/src/catalog/catalog.service.ts`
(`syncSingleFeed()`) уже парсит нужный XML и хранит всё необходимое в модели
`Lot` (Prisma, `@st-michael/database`):

- `externalId` = `offer['@_internal-id']` — **это тот же ProfitBase
  internal-id**, по которому нужно сопоставлять папки на Я.Диске (см. ниже,
  режим "по id"). Ключевое поле, других "своих" id для этого не нужно.
- `number` = сырой `offer.number` (например `"ЗГ3-2-3-22/1"`) — нужен для
  режима "по номеру квартиры" (корпус 3/Soho, см. ниже).
- `building` = `offer?.house?.name` (например `"Корпус 3. Soho"`) — по нему
  определять корпус (текстовый поиск `"Soho"` / `"Корпус 3"`, либо парсить
  первую цифру).
- `floor` уже хранится отдельным числом.
- `planImageUrl` — сейчас хранится **только одна** картинка (первая с
  `type="plan"`), остальные из фида **не сохраняются вообще** (строка ~71-73
  в `catalog.service.ts`). Это первое, что нужно поменять — см. ниже.

## Что нужно изменить в схеме данных

Сейчас `Lot` хранит одно поле `planImageUrl: string | null`. Нужно завести
массив фото (например `photos: String[]` в Prisma — Postgres умеет массивы
строк нативно) и мигрировать:

- `photos[0]` = текущий `planImageUrl` (первая картинка из фида) — либо просто
  оставить `planImageUrl` как есть для обратной совместимости и добавить
  отдельно `extraPhotos: String[]` (персональные + общие с Я.Диска), а
  итоговый порядок собирать на фронте/в API-ответе как
  `[planImageUrl, ...extraPhotos]`. Второй вариант проще и меньше ломает
  существующий код, читающий `planImageUrl`.
- В `apps/web` найти, где рендерится галерея лота (сейчас там судя по
  скриншоту всего одна картинка планировки с кнопкой "Увеличить") и добавить
  вывод остальных фото.

## Яндекс.Диск: источники и алгоритм

Всё через публичное API Яндекс.Диска, **без токена** — только `public_key`
(сама ссылка на публичную папку):

```
GET https://cloud-api.yandex.net/v1/disk/public/resources?public_key=<ссылка>&path=<путь>&limit=500
GET https://cloud-api.yandex.net/v1/disk/public/resources/download?public_key=<ссылка>&path=<путь>
```

Второй запрос отдаёт `{"href": "..."}` — прямую ссылку на файл. **Грабли:**
этот `href` отдаёт HTTP 302 redirect на реальный CDN-домен
(`downloader.disk.yandex.ru`) — если делать `fetch`/`curl` без обработки
редиректа, получите пустое тело с кодом 302. В `fetch` (Node) редиректы
следуются автоматически по умолчанию — в отличие от `curl`/PHP `curl_init`,
где нужно явно `CURLOPT_FOLLOWLOCATION`. Скорее всего в Node это не понадобится
явно указывать, но проверить при первом же тесте.

Также у API бывают 429/503 (rate limit) — нужен retry с экспоненциальным
бэкоффом (пробовали 7 попыток, `sleep(min(2^i, 30))` секунд), и между
скачиваниями файлов — пауза ~0.4 сек, чтобы не долбить API слишком часто.

Скачанные картинки нужно **кэшировать локально** (или в S3/объектном хранилище
— как принято в этом проекте) и раздавать со своего домена стабильными URL —
прямые ссылки Я.Диска подписанные и временные, в фид/API их вставлять нельзя.

### Источник 1 — персональные фото по id (все корпуса)

```
public_key: https://disk.360.yandex.ru/d/csRx3vArvfTcPA
```

Рекурсивно обходим папку. Подпапка, чьё имя содержит `id: <цифры>` (regex
`/id[:\s]*([0-9]{4,})/`), считается папкой лота — число сопоставляется с
`externalId` лота напрямую. Файлы-картинки внутри неё (тип `image/*`,
отсортированные по имени) — это его персональные фото. Если имя папки не
совпало с паттерном — спускаемся глубже (это просто промежуточная
папка-этаж/секция).

Совпадает примерно с 79 из ~1080 лотов (на момент реализации на
old.zorge9.com) — не для всех лотов есть фото, это нормально.

### Источник 2 — персональные фото по номеру квартиры (**только корпус 3 / Soho**)

```
public_key: https://disk.360.yandex.ru/d/m0i7Gq5M2G2n7Q
```

Другая структура: `<папка-этаж (число, напр. "02")>/<папка-секция, напр.
"А3">/<папка-лота, напр. "А3 (5) - 22.1">`. Листовая папка — та, чьё имя
оканчивается на `<число>.<число>` (regex `/(\d+)\.(\d+)\s*$/` — номер
квартиры и подиндекс через точку). Этаж берётся из **первого предка по пути**,
чьё имя — чисто число (например "02" → этаж 2); секция ("А3") в имени
папки-предка не несёт полезной информации для сопоставления, просто
структурная папка.

Сопоставление с лотом — по `number` (`"ЗГ3-2-3-22/1"` → берём последний
дефис-сегмент `"22/1"` → aptNum=`"22"`, subIndex=`"1"`) и `floor`:
`(floor, aptNum, subIndex)` → если нет точного совпадения по subIndex,
пробуем fallback `(floor, aptNum, "0")` (для квартир без подразделения на
студии, где в имени папки просто `"...22.0"` или подобное — на практике
регэксп на `\d+\.\d+` всегда даст какой-то subIndex, но fallback оставить на
всякий случай, как в опорной реализации).

**Применять этот источник только к лотам корпуса 3 (Soho) и только если по
Источнику 1 фото не нашлось** — так было решено на old.zorge9.com, чтобы не
делать бессмысленный полный обход этой папки для лотов, которых там
физически нет (в папке только корпус 3).

Совпало ~141 из ~380 лотов корпуса 3 на old.zorge9.com.

### Источник 3 — общие фото проекта (ВСЕ лоты, ВСЕ корпуса, без сопоставления)

```
public_key: https://disk.360.yandex.ru/d/6nA7DAS6HGlR1g
path:       /Для карточки проекта Авито
```

Это НЕ обход дерева — просто список файлов-картинок в этой ОДНОЙ папке
(без рекурсии). Скачать один раз, и эти же несколько картинок добавить в конец
фото **каждого** лота, во всех корпусах, без исключений — они одинаковые для
всего проекта (те же самые фото, что уже используются в `feed_enricher` как
`avito_extra_photos`).

## План реализации (предлагаемый)

1. Миграция Prisma: добавить `extraPhotos: String[]` (или `photos: String[]`,
   см. выше) в модель `Lot`.
2. Новый модуль/сервис, например
   `apps/api/src/catalog/yandex-disk-photos.service.ts`:
   - функции для трёх источников выше (обход дерева / список одной папки,
     скачивание файла с ретраями и редиректом, кэш на диске или в
     объектном хранилище);
   - функция `enrichLotsWithPhotos(lots)`, которая после `syncFromFeed()`
     проходит по всем лотам в БД и заполняет `extraPhotos`.
3. Вызывать `enrichLotsWithPhotos` сразу после `syncFromFeed()` — посмотреть,
   где сейчас планируется/крутится sync (`apps/api/src/scheduler/scheduler.service.ts`
   — там наверняка уже есть cron на `syncFromFeed`, повесить следующим шагом).
4. В API-ответе (`catalog.controller.ts`/`catalog.service.ts`, там где отдаётся
   лот) собрать финальный массив фото в нужном порядке: `[planImageUrl or all
   feed images] + extraPhotos-personal + extraPhotos-shared` — или проще
   всего просто собирать готовый итоговый массив в БД сразу в правильном
   порядке одним полем, чтобы не городить логику на каждый read.
5. На фронте (`apps/web`) найти компонент карточки/страницы лота (судя по
   скриншоту — `/apartments/[id]`) и вывести галерею вместо одной картинки.
6. Проверить на паре реальных лотов (включая хотя бы один корпуса 3), что
   порядок фото соответствует ожиданиям, и что общие фото проекта
   действительно применились ко всем лотам без исключения.

## Что НЕ переносить из old.zorge9.com

На старом сайте отдельно всплыла и была исправлена проблема с коллизиями
идентификатора лота (`корпус-этаж-позиция-на-этаже` не был уникален —
часть крупных лотов позже поделили на студии, и они схлопывались в один
слот). В этом проекте она **не актуальна**: здесь лот уже идентифицируется
по `externalId` (ProfitBase internal-id), который уникален по построению —
эта проблема сюда просто не переносится, чинить нечего.
