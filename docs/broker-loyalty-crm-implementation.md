# Broker Loyalty CRM: схема внедрения в кабинет

Дата решения: 18.08.2026.

Этот документ фиксирует архитектуру внедрения пакета `Broker Loyalty CRM` и
ограничения первого релиза. Исходный ZIP и содержащиеся в нём персональные
данные в репозиторий не добавляются.

Проверенный пакет: SHA-256
`482EA63DDD9030ACE255A4D50C9DDA8B631A8493D98B8FCE4948037533DA79DF`, 32
файла. В нём находятся ТЗ в DOCX/Markdown, карта read-only amoCRM, исходники
текущего дашборда, интеграционный контракт и audit examples.

Контрольная инвентаризация подготовленного снимка без вывода самих контактов:

- 6 670 уникальных нормализованных телефонов;
- 6 092 найдены в CRM, 578 не найдены;
- у 526 телефонов найдено несколько CRM-карточек;
- подготовленные агрегаты: 739 фиксаций, 375 встреч, 198 сделок,
  4 722 766 207 ₽;
- 2 620 карточек фиксаций и 517 карточек сделок требуют ручной проверки;
- 202 агентства, у 146 нет телефона, у 122 нет подтверждённых сделок.

Эти числа — результат аудита переданного пакета, а не утверждение о текущем
production. Они нужны для контроля следующего dry-run и не записываются в KPI
кабинета автоматически.

## Главное решение: две базы остаются раздельными

В интерфейсе создаётся отдельный раздел «База лояльности» с двумя независимыми
вкладками:

1. **База Анны Скибицкой** — данные только опубликованного снимка отдельного
   набора `ANNA`.
2. **Наша база** — текущее содержимое таблиц `Broker` и `Agency` кабинета в
   режиме чтения через адаптер модуля лояльности.

Внутри каждой вкладки есть собственные разделы «Брокеры» и «Агентства».
Фильтры и счётчики одного раздела не применяются к другому. Общей вкладки
«Все» нет.

Каждый из шести KPI имеет переход к данным: четыре количественных KPI открывают
список брокеров с серверным сегментом, построенным тем же предикатом, что и
счётчик; лидер по брокерам и лидер по агентствам открывают соответствующую
карточку по внутреннему UUID.

Совпадение телефона не переносит и не перезаписывает данные. Оно создаёт
кандидата на сверку. Только администратор может вручную подтвердить связь,
отклонить её или оставить записи раздельными. Подтверждённая связь также не
является слиянием: исходные карточки продолжают жить в своих базах.

## Почему нельзя использовать `Broker.baseSource`

Текущая карточка `Broker` имеет один уникальный телефон, один `amoContactId` и
одно строковое поле источника. Существующие импорты обновляют карточку на месте.
Это не позволяет сохранить:

- несколько amoCRM contact ID одного человека;
- несколько телефонов и исходные варианты номера;
- происхождение каждого значения;
- конфликтующие ФИО или агентства;
- воспроизводимый исторический снимок;
- откат публикации без изменения основной базы.

Поэтому база Анны реализуется отдельным bounded context с префиксом
`loyalty_`. Таблицы `brokers` и `agencies` при импорте не изменяются.

## Контур данных

```text
нормализованный UTF-8 JSON
        |
        v
dry-run: структура, лимиты, нормализация, ошибки, контрольные суммы
        |
        v
STAGED snapshot + immutable source records + provenance
        |
        v  явное действие ADMIN
PUBLISHED snapshot (атомарная смена активного снимка)
        |
        +--> вкладка «База Анны»
        |
        +--> reconciliation candidates --ручное решение--> cabinet link

Broker/Agency -------------------------------> вкладка «Наша база» (read-only)
```

Первый релиз намеренно не разбирает XLSX/TSV внутри API. Перед первой загрузкой
исходные таблицы должны быть преобразованы отдельным воспроизводимым конвертером
в версионированный JSON-контракт. Сам конвертер в этот релиз не входит; без него
исходный ZIP нельзя загружать в API напрямую. Такое разделение не позволяет
незаметно принять смещение колонок или формата дат за корректный импорт.

## Gap-матрица исходного кабинета

| Требование ТЗ | Сейчас в кабинете | Что переиспользуем | Что требуется модулю |
|---|---|---|---|
| Две независимые базы | Один `Broker` с одним `baseSource`; импорты делают upsert по телефону | PostgreSQL, Prisma, авторизацию | Отдельные `loyalty_*` таблицы, snapshot и read-only projection `OUR` |
| Карточка брокера | Один основной телефон/email/amo ID, дополнительные телефоны частично | UUID карточки, базовые данные, дизайн карточек | Коллекции контактов/amo ID, provenance, роли в агентствах, соцсети, качество данных |
| Карточка агентства | Реквизиты и M:N с брокерами; полноценной admin-карточки нет | Существующий `Agency` только для вкладки `OUR` | Отдельная организация, контактные лица, стадии, партнерство, БТ и договорённости |
| Шесть KPI | Есть иные локальные показатели | UI-карточки и общая сетка | Точные шесть формул, период рейтинга и drill-down до событий |
| Фиксации/встречи/сделки amoCRM | Локальные `Client`/`Meeting`/`Deal`; текущая аналитика использует другие правила | Транспорт и constants полей после изоляции read-only клиента | Полная пагинация, правила КЦ/проектных воронок, audit row и coverage report |
| Импорт Google | Читается один CSV и данные перезаписывают `Broker` | Нормализацию телефона как проверку | Четыре вкладки, immutable source records, dry-run, атомарная публикация |
| Сверка ~18 000 контактов | Частичный amo coverage по телефону | Ограниченные read-only запросы текущей базы | Группы конфликтов, reversible crosswalk, экспорт и журнал решений |
| Быстрый обзвон | Есть очередь брокеров и `CallLog`, но assignment хранится прямо в карточке | Mango-транспорт и часть UI звонка | Campaign/assignment/submission ID, очередь агентств, исчезновение обработанной строки |
| Роли | `BROKER`, `MANAGER`, `ADMIN` | JWT и guards | Сначала строгая матрица на существующих ролях, затем permissions |
| Аудит/удаление | Общий `AuditLog`, merge частично журналируется; есть hard delete | Формат audit actor/action/entity | Soft archive, old/new value, аудит импорта/экспорта/сверки |

Код опубликованного прототипа используется только как UX-референс. Его
`localStorage`, SQLite `REAL`, строковые кампании и физическое удаление в
кабинет не переносятся.

Основные гарантии:

- публикация целиком переключает активный снимок, частичный импорт не виден;
- каждый переход активного указателя, включая откат `A → B → A`, добавляется
  в отдельный журнал публикаций с предыдущим/новым snapshot ID и автором;
- повторный импорт того же содержимого идемпотентен по хешу записи;
- raw и normalized значения телефона хранятся раздельно;
- деньги хранятся как `Decimal`, даты — UTC;
- в KPI входят только активности с явным `verdict=INCLUDED`; `UNKNOWN` хранится
  для аудита и ручной проверки, но не увеличивает показатели;
- день рождения читается из `attributes.birthday` в формате `DD.MM`; если ни у
  одной карточки дата не известна, KPI показывает отсутствие данных, а не ноль;
- внешние ID уникальны в границах источника, типа сущности и ID;
- архивирование логическое, физического удаления через модуль нет;
- подтверждённая связь обратима отдельным действием `UNLINK`; каждое решение
  хранит автора и дату (поле комментария в первый релиз не входит);
- API не пишет в amoCRM;
- сырые строки и телефоны не попадают в application logs.

## Импорт и публикация

Рабочий порядок для каждой версии источника:

1. Администратор загружает нормализованный UTF-8 JSON (не более 10 МБ) в
   dry-run.
2. Система проверяет формат, максимальный размер/число записей, телефон,
   дубли внешних ID и обязательные связи.
3. Интерфейс показывает только агрегированные ошибки и счётчики, без полного
   дампа персональных данных.
4. Администратор создаёт снимок в состоянии `STAGED`.
5. До публикации сверяются количество строк, уникальных нормализованных
   телефонов и контрольная выборка.
6. Отдельной кнопкой публикуется весь снимок. Предыдущий опубликованный снимок
   остаётся доступен для аудита и отката указателя.

Импортный JSON обязан содержать контрольный манифест: `expectedRecords`,
`expectedUniquePhones`, `expectedActivities`, `expectedExternalIdentities`,
отдельные `expectedIncluded*` для фиксаций, встреч, сделок, брокер-туров и
звонков, а также точную Decimal-строку `expectedIncludedDealAmount`. Dry-run
пересчитывает все эти значения из строк и не разрешает staging при
расхождении — в том числе при первой публикации. При смене активного снимка
дополнительно сравниваются записи, брокеры, агентства, уникальные телефоны,
внешние ID, все активности, каждый тип активности `INCLUDED` и сумма сделок;
уменьшение любой размерности требует отдельного подтверждения для конкретной
пары старого и нового снимков.

Импорт из исходного пакета нельзя считать приёмочным без повторной выгрузки:

- физические количества строк TSV отличаются от audit JSON;
- два обязательных регрессионных контакта содержат старые агрегаты;
- число признаков БТ расходится на одну запись;
- часть сумм записана в миллионах/float вместо рублей Decimal;
- в прототипе остались старые статусы и необратимое удаление.

Пакет используется как структура, тестовые примеры и исходная гипотеза. Перед
боевой публикацией нужен новый read-only снимок Google/amoCRM и ручная проверка
не менее 50 случайных карточек.

## Сверка с нашей базой

Целевая полная сверка должна строить независимые группы:

- точное совпадение одного нормализованного телефона;
- один телефон соответствует нескольким карточкам;
- запись есть только у Анны;
- запись есть только в кабинете;
- нет валидного телефона;
- при совпавшем телефоне конфликтуют ФИО или агентство;
- контакт исключён или неактуален.

В текущем безопасном каркасе автоматически создаются кандидаты по точному
телефону, amoCRM ID и ИНН. Группы «только у Анны», «только в кабинете», записи
без валидного телефона и содержательные конфликты остаются следующим этапом и
не должны считаться уже рассчитанными.

Телефон — доказательство для кандидата, а не глобальная личность. ФИО не
используется для автоматического объединения. Доступные действия API:
`LINK`, `KEEP_SEPARATE`, `REJECT_MATCH`, `UNLINK`. `UNLINK` применим только к
ранее подтверждённой связи; смена активного снимка делает старый кейс
непригодным для новых решений, но сама активная связь остаётся доступна через
реестр связей и может быть отозвана по `linkId` с optimistic version check.
Новый кейс того же владельца и того же target также может безопасно подтвердить
и затем отозвать старую связь. Массового удаления и автоматического merge нет.

## Границы первого безопасного релиза

Реализуемый каркас даёт серверное хранение, отдельные вкладки, списки и
карточки, шесть метрик, staged import/publish и ручную сверку. До включения для
всех сотрудников отдельно выполняются следующие этапы:

1. Подключить read-only amoCRM integration и полный paginated snapshot.
2. Реализовать точные правила фиксаций, встреч и сделок с audit row на каждый
   включённый/исключённый lead ID.
3. Подключить все четыре вкладки Google и зафиксировать версию правил.
4. Добавить серверные кампании обзвона, assignment и уникальный submission ID.
5. Выполнить полную сверку примерно 18 000 контактов без mutation.
6. Провести regression-проверку контрольных контактов и выборку из 50 карточек.
7. Запустить пилот на одной группе, затем включить регулярное обновление.

До прохождения этих ворот показатели CRM маркируются как данные активного
опубликованного снимка, а не как live amoCRM. Это не позволяет принять
частичную выгрузку за актуальную истину.

## Этапы и ориентир оценки

Оценка дана для одного backend и одного frontend исполнителя с отдельным
временем владельца данных на контрольные выборки. Это не обещание даты релиза:
срок этапов 2–3 зависит от прав read-only amoCRM, качества Google-выгрузки и
доступности production snapshot кабинета.

| Этап | Результат | Ориентир |
|---|---|---:|
| 0. Аудит и модель | gap-матрица, схема, миграция, тестовые контракты | 3–5 рабочих дней |
| 1A. Справочники | две вкладки, брокеры/агентства, карточки, provenance, soft archive | 8–12 дней |
| 1B. Рабочие сценарии | фильтры, экспорт, кампании, быстрый обзвон, задачи/лояльность | 8–12 дней |
| 2. Источники | четыре Google-вкладки, GET-only amoCRM, формулы, полный audit | 10–15 дней |
| 3. Сверка и пилот | ~18 000 контактов, ручные решения, regression/50-card QA | 7–12 дней |

Этапы 1A/1B могут частично идти параллельно после фиксации схемы. Публикация
данных и регулярный scheduler включаются только после окончания этапа 2.

## Неблокирующие и блокирующие входы

Каркас, API и UI можно разрабатывать без production-доступа. Для ввода данных
в эксплуатацию понадобятся:

- свежий полный экспорт всех четырёх вкладок Google либо service account с
  read-only доступом;
- отдельные read-only credentials amoCRM и подтверждение официального OAuth
  refresh-потока;
- production snapshot/count нашей базы для полной сверки;
- подтверждение владельцем неоднозначного соответствия кампаний Май–Август;
- согласование правила «Спящий» для подарка как типа активности;
- список пользователей кабинета, которым выдаются permissions руководителя,
  оператора, аналитика и наблюдателя;
- решение по сроку хранения raw source records и экспорта ПД.

## Доступы

Существующие роли кабинета используются без расширения enum на первом этапе:

- `ADMIN`: импорт, публикация, редактирование карточек базы Анны, сверка и
  аудит решений;
- `MANAGER`: чтение обеих вкладок и рабочих показателей;
- `BROKER`: раздел недоступен.

Перед вводом очередей обзвона роли следует заменить отдельными permissions
(`loyalty.read`, `loyalty.import`, `loyalty.reconcile`, `call.assign`,
`call.execute`, `loyalty.export`), не добавляя строковые списки сотрудников в
код.

## Проверка перед выкладкой

- миграция применяется на копии production schema;
- dry-run не создаёт и не изменяет `Broker`/`Agency`;
- публикация недоступна `MANAGER` и `BROKER`;
- запросы базы Анны всегда ограничены активным snapshot;
- запросы «Нашей базы» не возвращают данные во вкладку Анны;
- API ограничивает page size и объём импорта;
- решения сверки записывают actor ID и не удаляют карточки;
- секреты/PII отсутствуют в git, CI output и логах;
- backup и процедура отката активного snapshot проверены до migration.
