# Восстановление одной фиксации amoCRM

Этот регламент относится только к клиенту `8d082b21-7cba-4778-a6c6-1d80bfe7ed7c` и исключаемому лиду `32372907`. Расширять область действия подстановкой других идентификаторов нельзя.

## Обязательная последовательность

1. Дождаться успешного CI workflow `deploy.yml` для текущего `master`.
2. Запустить workflow `Plan or recover approved single amo fixation case once` в режиме `plan` с подтверждением `PLAN_FIXED_AMO_CASE_READONLY`. Остальные поля оставить пустыми.
3. Проверить безопасный отчёт: `status=planned`, `mutationAuthorized=false`, `databaseWrites=false`, `amoWrites=false`. Зафиксировать run ID, `caseHash`, `candidateHash` и `deployedGitSha`. Отчёт действителен 30 минут.
4. До любых изменений вручную сверить карточку `32372907`: это отдельное Calltouch-обращение брокера, а не карточка данного клиента. Любое расхождение останавливает процедуру.
5. Создать свежую штатную резервную копию workflow `backup-production-loyalty-predeploy.yml` для того же SHA `master`.
6. Только после повторного ревью под подтверждённой учётной записью `mefremov888-ai` запустить тот же workflow в режиме `apply`: передать plan run ID, оба хэша, `deployedGitSha`, CI run ID, backup run ID и подтверждение `RECOVER_APPROVED_FIXED_AMO_CASE_ONCE`. Workflow откажет другому actor, поскольку GitHub environment `production` сам по себе не настроен как approval gate.

Apply повторно вычисляет хэши под эксклюзивной блокировкой, перечитывает сертификат старого лида перед каждой границей записи и перед связыванием результата и прекращает работу при любом изменении. Разрешены максимум один `POST /contacts`, один `POST /leads`, один `PATCH /leads/{id}` со всеми обязательными полями и один POST заметки. Стандартный tracking fallback адаптера в этом exact-case пути не вызывается. Потерянный ответ сверяется только GET-запросами и никогда не вызывает повторную запись.

## Что считается успехом

До локального статуса `SYNCED` должны быть подтверждены:

- новый контакт клиента и новый лид с точными связями клиента и брокера;
- обязательные поля анкеты, проекта, признака «от брокера» и времени заявки;
- единственная точная заметка с данными формы, recovery UUID, source tag и agency tag;
- отсутствие любого дополнительного кандидата, кроме сертифицированного `32372907` и нового лида;
- неизменность владельца, ответственного брокера, агентства, статусов уникальности/фиксации и остальных бизнес-полей;
- успешный CAS и readback базы, включая новое `amoSyncLastAttemptAt`. Статус фиксации остаётся `NOT_FIXED`; операция не объявляет клиента уникальным или зафиксированным.

## Необратимые внешние эффекты

Резервная копия PostgreSQL не удаляет контакт, лид или заметку из amoCRM. Создание лида может запустить обычные Salesbot/Morekit-автоматизации amoCRM, хотя workflow сам Morekit не вызывает.

При `unresolved`, потере блокировки, таймауте после POST или ошибке локального CAS:

1. Не перезапускать apply и не удалять объекты автоматически.
2. Сохранить run ID и безопасный failure code.
3. Выполнить только GET-only сверку amoCRM и локальных audit-записей.
4. Вручную определить, был ли создан контакт/лид/заметка и были ли запущены автоматизации.
5. Любое удаление, перенос или слияние внешней карточки оформлять отдельным планом и отдельным подтверждением. Этот workflow таких действий не выполняет.
