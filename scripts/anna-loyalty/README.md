# Конвертер базы Анны Скибицкой

Конвертер читает исходный ZIP `Broker Loyalty CRM`, проверяет его SHA-256 и
создаёт JSON для контракта `LoyaltyImportDto`. TypeScript-файлы внутри ZIP не
исполняются: из двух известных экспортов извлекаются только строгие JSON-массивы.
Неизвестные поля, исполняемые выражения, повреждённый ZIP и несовпадающий hash
останавливают обработку.

Исходный ZIP и полученный JSON содержат персональные данные. Их нельзя добавлять
в Git, CI artifacts, issue, PR или отправлять в чат. Конвертер пишет в консоль
только hash, размеры и агрегированные количества.

## Проверенный источник

- SHA-256:
  `482ea63ddd9030ace255a4d50c9dda8b631a8493d98b8fce4948037533da79df`;
- экспорт брокеров: `source-package/current-dashboard/app/broker-source-enriched.ts`;
- экспорт агентств: `source-package/current-dashboard/app/crm-agencies.ts`.

Другой пакет по умолчанию отклоняется. Для заранее проверенной замены нужно
явно передать `--expected-sha256 <64-hex>`; этот параметр не отключает проверку,
а заменяет ожидаемый hash.

## Запуск

Сначала только отчёт, без файла с персональными данными:

```powershell
node scripts/anna-loyalty/convert.js `
  --zip "C:\path\Broker_Loyalty_CRM_пакет_для_кабинета_2026_08_17.zip" `
  --report-only
```

После сверки агрегатов создать файл **за пределами репозитория**:

```powershell
node scripts/anna-loyalty/convert.js `
  --zip "C:\path\Broker_Loyalty_CRM_пакет_для_кабинета_2026_08_17.zip" `
  --output "C:\secure-temp\anna-loyalty-import.json"
```

Существующий output не перезаписывается. Файл создаётся завершённым через
временный файл и hard link; запрашивается режим `0600`. На Windows POSIX mode
не равен ACL: каталог назначения должен заранее быть доступен только оператору.
После импорта файл и его временные/сжатые копии нужно удалить утверждённой
защищённой процедурой.

Тесты не содержат реальные данные:

```powershell
node --test scripts/anna-loyalty/convert.test.js
```

## Что переносится

- все 6 670 строк брокеров и 202 строки агентств;
- исходные/дополнительные контакты, включая структурированные контактные лица
  агентств;
- все amoCRM contact/company ID; два ID, встречающиеся у разных брокерских
  строк, сохраняются как конфликт и не объединяют записи;
- имена и алиасы, компания, роль, специализация, география, качество данных,
  комментарий и источники;
- история обзвонов без выдуманных дат;
- предварительные source-reported агрегаты amoCRM отдельно от подтверждённых
  `activities`;
- точная десятичная конвертация agency `sales` из `MILLION_RUB` в RUB;
- только однозначная связь брокера с агентством по exact-match эффективного
  `crm.company || row.company` с нормализованным набором
  `name/company/aliases/crmNames` агентства.

Счётчики, последние даты и история без event ID не превращаются в
`FIXATION/MEETING/DEAL/CALL`. Поэтому `expectedActivities` и все
`expectedIncluded*` равны нулю, а исходные показатели живут в
`sourceAggregate` с `quality=SOURCE_REPORTED` и `exactness=UNKNOWN`.
`expectedSourceReportedSummary` считается независимо из готовых записей и
разделяет `BROKER` и `AGENCY`.

История Google хранится компактно и без потерь в
`attributes.history` как tuple:

```text
[label, rawValue, normalizedResult, campaignMonth|null]
```

Отсутствие пятого элемента означает `occurredAt=unknown`. Месяц кампании —
только атрибуция; его запрещено считать датой звонка. Датированные наблюдения
`callsMayAugust` остаются в `sourceAggregate.callBreakdown`, но также не
становятся событиями.

## Стабильные ключи и проблемные телефоны

В исходнике брокера нет отдельного неизменяемого row ID. Для валидного телефона
используется namespaced SHA-256 нормализованного номера. Он не раскрывает номер
в ключе и не объединяет человека по имени. Изменение телефона намеренно создаёт
новую запись для ручной сверки.

Пять строк имеют 11-значные номера с префиксом `77`; по правилам v3 это
невалидный/усечённый номер. Строки не теряются, но PHONE contact point для них
не создаётся. Они получают `exclusionCandidate=INVALID_PHONE`,
`matchable=false`; ключ берётся из уникального amoCRM contact ID, а при его
отсутствии — из namespaced hash исходной строки. Телефон остаётся только в
защищённых source-attributes/provenance и не участвует в сопоставлении.

Агентства используют hash стабильного `crm-agencies.id`. Телефон, имя или
совпавший amoCRM ID никогда не сливают две исходные строки автоматически.

до появления event-level evidence.

## Лимит и доставка

Лимит проверяется по фактическому UTF-8 JSON без pretty-print и без перевода
строки в конце — именно этот buffer записывается на диск. Текущий canonical
payload занимает 10 426 832 байта при лимите 10 485 760. Любое увеличение или
изменение контракта должно снова пройти report-only; нельзя молча выбрасывать
поля или увеличивать HTTP-лимит.

Для защищённой production-доставки ориентируйтесь на
`docs/anna-loyalty-production-import.md`. Конвертер дополнительно сообщает
размер deterministic gzip, base64 и число частей по 45 000 символов, но сам не
загружает данные и не меняет БД.
